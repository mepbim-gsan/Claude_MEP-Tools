# DD-MEP タスク管理ダッシュボード 要件定義書

作成経緯：claude.ai（チャット形式）で対話しながら段階的に構築。
今後は Claude Code に開発を引き継ぐため、現状の仕様をまとめたもの。

対象ファイル: `task-dashboard.html`（単一HTMLファイル、外部依存なし。フォント・CDN等も不使用）

---

## 1. 目的・背景

- Teams の投稿を SharePoint リストで一覧管理し、各投稿に「ステータス」列を付与してタスク管理として運用している
- Power Automate で毎日、SharePoint リストの内容を JSON ファイルとして書き出している（`ddmep_team.json` など）
- 本ツールはその JSON を読み込み、状況を可視化・絞り込みできるダッシュボード
- 開発中は「ファイル選択」でローカルJSONを読み込む方式。本番運用時は SharePoint 上の同一オリジンから `fetch` する方式に切り替え予定（詳細は9章）

## 2. データソースの形式

### 2.1 タスクJSON（Power Automate 書き出し）

トップレベルが `{"body": [...]}` の配列（`value` キーでも許容）。1件の例：

```json
{
  "id": 1,
  "title": "【ご相談】AEライブラリのフォルダ構成について",
  "date": "2024-08-08T09:38:00Z",
  "url": "https://teams.microsoft.com/l/message/...",
  "channel": "チャネル_RVT",
  "targetDate": null,
  "completedDate": "2024-09-06",
  "modified": "2025-04-30T05:25:38Z",
  "messageId": "1723109851610",
  "channelId": null,
  "relMessageId": null,
  "relChannelId": null,
  "author": "氏名1",
  "owner": "氏名2",
  "members": [
    {
      "@odata.type": "#Microsoft.Azure.Connectors.SharePoint.SPListExpandedUser",
      "Claims": "i:0#.f|membership|...",
      "DisplayName": "氏名2",
      "Email": "...",
      "Picture": "...",
      "Department": "本社統括グループ",
      "JobTitle": null
    }
  ],
  "status": "完了",
  "relWork": null
}
```

主要フィールドの役割分担（重要・混同しやすい）：

| フィールド | 役割 | 備考 |
|---|---|---|
| `author` | 投稿者（Teamsにそのメッセージを最初に投稿した人） | テキスト |
| `owner` | 担当者（タスクの主担当、1名） | テキスト |
| `members` | 関係者（Person型、複数可） | `DisplayName` を使用 |
| `status` | ステータス（選択肢列。値は運用上変動し、固定リストではない） | 例：未着手／進行中／保留／完了／周知 等、可変 |
| `channel` | Teamsのチャネル名。タスク系チャネルと周知・会議系チャネルが混在 | チャネルで「分野・タスク種別」を区別、ステータスで「作業状況」を可視化する運用 |
| `date` | 投稿日 | |
| `modified` | 更新日 | |
| `targetDate` | 期限（あれば） | |
| `url` | Teamsメッセージへのリンク | |
| `completedDate` | 完了日（あれば） | 現状アプリ未使用 |
| `messageId` / `channelId` | Teams上のメッセージ／チャネルのID | 現状アプリ未使用 |
| `relWork` | 関連WORK（バックログ「WORK単位のタスク管理」用） | SharePointリスト側に列は作成済み。値投入・活用の仕組みは未整備、現状アプリ未使用 |
| `relMessageId` / `relChannelId` | 関連スレッドの参照ID（バックログ「スレッド更新のリスト反映」用） | SharePointリスト側に列は作成済み。値投入・活用の仕組みは未整備、現状アプリ未使用 |

**重要な仕様**：関係者(`members`)には SharePoint 側の仕様で担当者(`owner`)と同じ人も重複して入ってしまうため、アプリ側で「担当者と同名の人物は関係者から除外する」ロジックを入れている（後述 `getMemberNames`）。

### 2.2 複数リスト対応

- ファイル選択は `multiple` 属性で複数ファイル選択可能
- 各タスクに読み込み元ファイル名（拡張子除く）を `_sourceList` として付与し、内部的に統合管理
- 「リスト」フィルタで絞り込み可能（一覧テーブルには列としては表示しない。チャネルで判別できるため）

### 2.3 Setting.json（チーム共有設定）

ファイル名が `Setting.json`（大文字小文字不問）の場合、データではなく設定ファイルとして自動判別・分離読み込みされる。データJSONと同時選択も可。

```json
{
  "statusGroupMap": { "進行中": "稼働系", "未着手": "稼働系", "保留": "保留系" },
  "hiddenPeople": ["退職済みの人の氏名"],
  "groupOrder": ["稼働系", "保留系", "完了・中止"],
  "defaultStatuses": ["未着手", "進行中"],
  "defaultChannels": ["T_MEP設備"],
  "statusColorMap": { "進行中": "#2563eb", "完了": "#16a34a" }
}
```

保存の二層構成：
1. **Setting.json**（基本・チーム共有、同じ場所に配置してチームで共有）
2. **localStorage**（個人上書き。画面操作は即座に自動保存される。存在する場合はSetting.jsonより優先）

設定タブから「Setting.jsonをダウンロード」でエクスポート、「個人上書きをリセット」でlocalStorageをクリア可能。

## 3. 画面構成（タブ）

上部にタブ切替：**一覧 / チャネル別 / 担当者別 / 設定**（タイトル・ロード欄を含むヘッダーごとスクロール時も画面上部に固定表示される `sticky-header`）
- タブ行の右側に「絞り込み中」表示＋「条件クリア」ボタン（`#filterStatus`）。いずれかのフィルタが有効な間だけ表示され、どのタブからでも一括クリアできる（`hasActiveFilters()`で判定）

### 3.1 「一覧」タブ

- **サマリーカード**：総件数＋ステータス別件数（クリックでトグル絞り込み、複数選択可）
  - 表示モード切替：「グループ別」（初期値）／「ステータス別」
  - グループ別モード：`statusGroupMap` でグループ化されたステータスは合算1枚のカードに。同グループ内が一部だけ選択中の場合は「一部選択中」の表現（オレンジ破線＋n/m件選択中）
  - 「(未設定)」ステータスは常に先頭（グループ内タイブレークとしても最優先）
- **役割パネル（担当者・関係者・投稿者の集計表）**
  - `<details class="role-panel-details">`で折りたたみ可能。**初期状態は閉じている**（縦スペース節約のため。フルHD等の画面でもタスク一覧が見える範囲に多く収まるように）。開閉状態はセッション内のみ（保存はしない）
  - 表形式：氏名／担当／関係／投稿の列。担当者数の多い順にソート
  - 各数値セルは列内最大値に対する比率でCSSグラデーション背景バー（簡易グラフ表示）
  - 先頭に「(未設定)」行：担当者なし／関係者0人／投稿者なしの件数を集計
  - 行全体をタップ → その人の担当・関係・投稿タグをまとめてON/OFF（3つ全部揃っている場合のみ「有効」表示）
  - 個別の数値バッジをタップ → その役割だけ個別にON/OFF可能（例：担当者と関係者だけ選び、投稿者は除外、という絞り込みができる）
  - この集計は現在の「チャネル」「ステータス」絞り込みを反映する（自分自身の役割タグ選択は除外して計算し、循環参照を防止）
- **フィルタ**：タイトル文字列検索（フリーテキスト、部分一致）／チャネル（`T`始まり＝タスクチャネル／その他でグループ分けした複数選択パネル、`activeChannels`）／リスト（プルダウン、単一選択）／期間絞り込み（投稿日・更新日・期限のいずれかを選択し、開始日〜終了日で範囲指定）／条件クリアボタン
  - チャネルパネルは開閉式（`<details>`）。各グループに「全選択」「全解除」ボタン。選択件数に応じてサマリー表示が「チャネル：すべて」⇔「チャネル：n件選択中」に切り替わる
- **一覧テーブル**：タイトル（Teamsリンク）／編集リンク（鉛筆アイコン、後述）／ステータス／担当者／関係者／投稿者／チャネル／投稿日／更新日
  - 投稿日・更新日はヘッダークリックでソート切替（▲▼表示）。初期値は投稿日の降順
  - 日付表示は `yyyy/mm/dd`（ゼロ埋め）
  - 担当者・関係者・投稿者は「表示しない人」設定を反映（`getOwnerName`/`getAuthorName`/`getMemberNames` 経由、非表示者は "(未設定)" 扱い）
  - チャネル名クリック → そのチャネル1件だけを選択状態にする（`activeChannels = new Set([チャネル名])`、`.channel-link`、一覧タブ内なので画面遷移なし）

### 3.2 「チャネル別」タブ

- チャネル × ステータスのマトリクス表（件数）。**このタブの役割はチャネル×ステータスの検索窓口**であり、
  一覧タブの現在のチャネル選択（`activeChannels`）とは関係なく全チャネルを表示する
  （`getFiltered({exclude:['channel']})`）
- 行（チャネル）はチャネル名の五十音順（`localeCompare('ja')`）
- 列（ステータス）は「グループの並び順 → 同グループ内は(未設定)優先 → 件数の多い順」（`statusDisplayComparator` 関数で共通化。他画面のステータス表示順もすべてこれに準拠）
- セルクリック → 一覧タブに遷移し、該当チャネル1件だけを選択状態にして該当ステータスで絞り込み
  （`activeChannels = new Set([チャネル名])`）

### 3.3 「担当者別」タブ（タスクボード形式）

- 担当者選択はプルダウン（選択肢に「未完了n／全n」を表示、未完了が多い人が上位。この件数は一覧タブのフィルタを反映しない全体件数）
  - 選択すると`activeRoleTags`を`owner:氏名`一本に置き換え、一覧タブ（サマリーカード・役割パネル・テーブル）にもその担当者の絞り込みが反映される。「未選択」に戻すと`activeRoleTags`もクリアされる。担当者別で見ている人と一覧タブの表示がズレないようにするための双方向同期（3.1の自動選択と対）
- 一覧タブのステータス／テキスト／期間フィルタは担当者別タブの表示にも反映される（`getFiltered({exclude:['roleTags','channel']})` を担当者でさらに絞り込み）。`activeRoleTags`は対象外（担当者選択プルダウン自体が役割絞り込みを兼ねるため、二重適用による意図しない0件化を避けている）
- **チャネルは対象外**（2026-07-27.2〜）：一覧タブの`activeChannels`は担当者別タブに反映されない。担当者別タブは「特定の担当者の現状把握」に特化したタブとして、チャネル絞り込みもタブ内だけで完結する専用のローカル状態`ownerChannelFocus`を持つ（3.3後半参照）。タブをまたいで状態が食い違って見える混乱を避けるための設計方針（4章末尾参照）
- ただし`activeRoleTags`が指す人物が1人だけに定まる場合（役割は問わない。氏名タップで担当/関係/投稿の3タグが一括ONになるケースを含む）、担当者別タブを開いた瞬間にその人をプルダウンで自動選択する（`singleImpliedPerson`/`applyImpliedOwnerSelection`）。2人以上を指している場合や該当者がプルダウンに存在しない場合は何もしない（既存の選択を維持）
- 選択するとその人のタスクをステータスごとにカード表示（優先度の高い「未完了」を目立たせる）
  - `RESOLVED_STATUSES`（現在は `['完了']`）に含まれるステータスは自動的に「完了」として折りたたみ表示（`<details>`）
  - 未完了カードは期限（`targetDate`）昇順→期限なしは投稿日降順でソート、期限があれば赤字表示
  - タイトル前に編集リンク（鉛筆アイコン）を表示（一覧タブと同じ`renderEditLink`/`EDIT_LINK_CONFIG`を共用）
  - メタ情報（チャネル／期限／投稿日）はCSS gridで列位置を固定し、カードごとに揃うようにしている（チャネル名の長さや期限の有無に関わらずズレない）
  - チャネル名クリック → **一覧タブへは遷移せず**、担当者別タブの中だけでそのチャネルに絞り込む（`ownerChannelFocus`、単一チャネル）。同じチャネルを再クリックすると解除（トグル）。表示された「チャネル「◯◯」で絞り込み中」の解除ボタンでも解除できる。担当者を切り替えると自動的にリセットされる（2026-07-27.2〜。以前は一覧タブへ遷移して全体のフィルタを書き換える仕様だったが、タブをまたいで絞り込み状態が食い違って見えるとの指摘を受けて変更。チャネル別タブのマトリクスセルクリックは検索窓口としての役割のため、引き続き一覧タブへ遷移する）
- ステータス表示のON/OFFチップ（`hiddenStatuses`）で、特定ステータスのセクションを個別に非表示にできる
  - チップ自体の選択肢（`renderOwnerStatusToggle`）も一覧タブのフィルタを反映して`renderAll()`のたびに再構築される。フィルタで対象外になったステータスのチップは表示されない（担当者選択肢と異なり、こちらはフィルタ非依存にしていない点に注意）

### 3.4 「設定」タブ

1. **ステータスのグループ化**
   - 各ステータスにプルダウンでグループを割り当て（新規グループ名も作成可、`window.prompt`で入力）
   - グループの並び替え（▲▼ボタン）、名称変更（同グループ内の全ステータスに一括反映）
   - 空になったグループは自動的にリストから消える（`syncGroupOrder`）
2. **表示しない人（退職済みなど）**
   - チェックした人は担当者・関係者・投稿者の選択肢・集計から除外され、"(未設定)" 扱いになる（データ自体は保持）
3. **一覧タブの初期ステータス絞り込み**
   - チェックしたステータスが、データ読み込み時に自動的にサマリーカードでON状態になる
4. **ステータスのカラー設定**
   - 各ステータス行の色スウォッチ（`<input type="color">`）から手動で色を変更可能
   - 指定した色は `settings.statusColorMap`（ステータス名→HEX色）として保存され、`colorForStatus` は自動採番より優先してこの値を返す
   - 未指定のステータスは従来通り `COLOR_PALETTE` から自動採番

## 4. フィルタ・絞り込みの仕組み（重要）

`getFiltered(options)` が中心のフィルタ関数。`options.exclude` で特定の絞り込み軸だけ除外して再計算できる（例：グラフ自身の選択が自分自身の表示に影響しないようにするため）。

絞り込み軸は以下の系統：

1. **`activeStatuses`（Set）**：サマリーカードでトグル。複数選択はOR、他の軸とはAND
2. **`activeChannels`（Set）**：一覧タブのチャネルフィルタパネルでチェック。複数選択はOR、他の軸とはAND
   （`T`始まり＝タスクチャネル／その他でグループ分け表示。2026-07-27〜、旧`channelFilter`プルダウン単一選択から変更）
3. **リスト（プルダウン、単一選択）**：`listSourceFilter`
4. **`activeRoleTags`（Set）**：役割パネル発。`"owner:氏名"` `"member:氏名"` `"author:氏名"` の形式のタグを持ち、活性化しているタグ群は「いずれか一致すればOK」というOR条件。他の軸とはAND
   - 担当者別タブの担当者プルダウンとも双方向に同期する：一覧側で1人だけに絞り込むと担当者別で自動選択（3.3）、担当者別でプルダウンを変更すると`activeRoleTags`が`owner:氏名`一本に置き換わる（3.3）
5. **タイトル文字列検索（`textFilter`）**：部分一致・大文字小文字区別なし。他の軸とはAND
   - チャネル名クリック（`.channel-link`）は一覧タブ・チャネル別タブでは`activeChannels`をそのチャネル1件に置き換えるショートカット。担当者別タブでは`activeChannels`に触れず、タブ内だけで完結する`ownerChannelFocus`を使う（後述の「タブごとの役割分離」参照）
6. **期間絞り込み（`dateFilterField`/`dateFilterFrom`/`dateFilterTo`）**：対象フィールド（投稿日/更新日/期限）を選び、開始日・終了日のいずれか片方のみの指定も可。対象フィールドが空値の項目は範囲指定時に除外される。他の軸とはAND

`activeRoleTags` の `member:(未設定)` は「関係者が0人」、`owner:(未設定)` `author:(未設定)` はそれぞれ getOwnerName/getAuthorName が "(未設定)" を返すケースにマッチ。

**適用範囲**：
- 一覧タブ：`activeStatuses`/`activeChannels`/`activeRoleTags`/テキスト/期間/リストのすべてを反映
- チャネル別タブ：`renderMatrix`は`getFiltered({exclude:['channel']})`で反映（自軸のチャネルだけ除外し、他の全チャネルを見せて検索窓口として機能させる）
- 担当者別タブ：`getFiltered({exclude:['roleTags','channel']})`で反映。ステータス/テキスト/期間/リストは一覧タブと共有するが、チャネルは共有せず`ownerChannelFocus`で独自に絞り込む

全タブから参照できるよう、タブ行に「絞り込み中」表示＋「条件クリア」ボタンを常設（3章参照）。この`hasActiveFilters()`/`resetFilters`は`activeStatuses`/`activeChannels`/`activeRoleTags`/テキスト/期間/リストが対象で、タブローカルな状態（`hiddenStatuses`、`ownerChannelFocus`）は対象外（各タブ内の表示だけを絞り込むものであり、全体の「絞り込み中」表示に含めると却って混乱するため）。

### タブごとの役割分離の設計方針（2026-07-27.2〜）

一覧タブの複数選択チャネルフィルタを導入した直後、「チャネル別タブ・担当者別タブでチェック状態が反映されているように見えない」という指摘があった。対応として、チャネルに関しては「グローバルな状態を全タブで同期して見せる」のではなく、**タブごとに役割を分離して完結させる**方針を採用した：

- **チャネル別タブ**：チャネル×ステータスのマトリクス検索窓口。セルクリックで一覧タブへ遷移するのは目的に合っており、そのまま維持
- **担当者別タブ**：特定の担当者の「今の状況」を把握する場所。チャネル名クリックは一覧タブへ飛ばさず、タブ内だけで絞り込む（`ownerChannelFocus`）

ステータス・テキスト・期間・リストの各フィルタは従来どおり一覧タブと担当者別タブで共有する（この方針変更の対象はチャネルのみ）。

過去に存在したが**廃止した仕組み**（Claude Codeで復活させないよう注意）：
- 担当者別の単独棒グラフ（`ownerChart`）→ 役割パネルに統合したため削除
- ステータス別の棒グラフ（`statusChart`）→ サマリーカードのトグルに統合したため削除
- 「自分の役割で絞り込み」の単一選択ドロップダウン（`selfFilter`）→ 役割パネルに置き換え
- 担当者・関係者・投稿者それぞれの単独プルダウン（`ownerFilter`/`memberFilter`/`authorFilter`）→ 役割パネルに統合
- チャネルの単一選択プルダウン（`channelFilter`）→ 複数選択パネル（`activeChannels`）に置き換え（2026-07-27）

## 5. 「表示しない人」ロジックの詳細

- `getOwnerName(item)` / `getAuthorName(item)` / `getMemberNames(item)` の3関数経由でのみ担当者・投稿者・関係者を参照する設計。**`item.owner` 等を直接参照しているコードがあれば、それはバグ（非表示設定が反映されない）**
- `getMemberNames(item)` は以下を満たす名前だけを返す：
  1. `settings.hiddenPeople` に含まれていない
  2. その項目の `item.owner`（担当者）と同名でない（＝担当者と関係者の重複除去）

## 9. 本番移行（SharePoint fetch化）に関する検討結果

現在の「ファイル選択で読み込み」を、本番では `fetch()` に切り替える想定だが、検討の結果、以下の技術的制約が判明している。

1. **SharePointドキュメントライブラリの `.html` は直接開いてもレンダリングされない**
   モダンSharePoint Onlineは `.html` ファイルに強制ダウンロードヘッダーを付与し、ブラウザでの実行を許可しない（セキュリティ上の既定仕様）。
2. **クロスオリジンfetchはCORSでブロックされる**
   ツールを別オリジン（社内HTTPサーバー、GitHub Pages等）に置き、SharePointのデータをfetchしようとするとCORSに阻まれる。回避には基本的にAzure AD (Entra ID) アプリ登録が必要（情報システム部門の確認が必要、未確定）。
3. **OneDriveも別オリジン**（`{テナント}-my.sharepoint.com` は `{テナント}.sharepoint.com` と別ホスト）であり、SharePointへのfetchはCORS対象になる。HTMLの直接レンダリングについても、OneDriveの方がSharePointより開ける場合があるとの非公式情報はあるが、公式に保証された仕様ではなく、本番の前提にはできない。
4. **Power AutomateからオンプレHTTPサーバーへの直接書き込み**にはオンプレミスデータゲートウェイが必要（情シス確認・管理が必要）。

**現時点で最有力の方針**：
SharePointドキュメントライブラリを、社内HTTPサーバー機に「OneDrive同期クライアント」で同期し、同期先ローカルフォルダをそのまま社内HTTPサーバーで配信する。ツール（HTML）とデータ（JSON）が同一オリジンになるため、CORSもAD登録もカスタムスクリプト制限も回避できる。API呼び出し自体が不要になる。

→ この場合、コード上の変更は「ファイル選択(`<input type="file">`)を`fetch(相対パス)`に差し替えるだけ」で済む想定（データ構造・関数群はそのまま流用可能）。
