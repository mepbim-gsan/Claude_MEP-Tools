# DD-MEP タスク管理ダッシュボード 要件定義書

作成経緯：claude.ai（チャット形式）で対話しながら段階的に構築。
今後は Claude Code に開発を引き継ぐため、現状の仕様をまとめたもの。

対象ファイル: `task-dashboard.html`（単一HTMLファイル、外部依存なし。フォント・CDN等も不使用）

---

## 1. 目的・背景

- Teams の投稿を SharePoint リストで一覧管理し、各投稿に「ステータス」列を付与してタスク管理として運用している
- Power Automate で毎日、SharePoint リストの内容を JSON ファイルとして書き出している（`ddmep_team.json` など）
- 本ツールはその JSON を読み込み、状況を可視化・絞り込みできるダッシュボード
- 開発中は「ファイル選択」でローカルJSONを読み込む方式。本番運用時は SharePoint 上の同一オリジンから `fetch` する方式に切り替え予定（詳細は9章）

## 2. データソースの形式

### 2.1 タスクJSON（Power Automate 書き出し）

トップレベルが `{"body": [...]}` の配列（`value` キーでも許容）。1件の例：

```json
{
  "id": 1,
  "title": "【ご相談】AEライブラリのフォルダ構成について",
  "date": "2024-08-08T09:38:00Z",
  "url": "https://teams.microsoft.com/l/message/...",
  "channel": "チャネル_RVT",
  "targetDate": null,
  "completedDate": "2024-09-06",
  "modified": "2025-04-30T05:25:38Z",
  "messageId": "1723109851610",
  "channelId": null,
  "relMessageId": null,
  "relChannelId": null,
  "author": "氏名1",
  "owner": "氏名2",
  "members": [
    {
      "@odata.type": "#Microsoft.Azure.Connectors.SharePoint.SPListExpandedUser",
      "Claims": "i:0#.f|membership|...",
      "DisplayName": "氏名2",
      "Email": "...",
      "Picture": "...",
      "Department": "本社統括グループ",
      "JobTitle": null
    }
  ],
  "status": "完了",
  "relWork": null
}
```

主要フィールドの役割分担（重要・混同しやすい）：

| フィールド | 役割 | 備考 |
|---|---|---|
| `author` | 投稿者（Teamsにそのメッセージを最初に投稿した人） | テキスト |
| `owner` | 担当者（タスクの主担当、1名） | テキスト |
| `members` | 関係者（Person型、複数可） | `DisplayName` を使用 |
| `status` | ステータス（選択肢列。値は運用上変動し、固定リストではない） | 例：未着手／進行中／保留／完了／周知 等、可変 |
| `channel` | Teamsのチャネル名。タスク系チャネルと周知・会議系チャネルが混在 | チャネルで「分野・タスク種別」を区別、ステータスで「作業状況」を可視化する運用 |
| `date` | 投稿日 | |
| `modified` | 更新日 | |
| `targetDate` | 期限（あれば） | |
| `url` | Teamsメッセージへのリンク | |

**重要な仕様**：関係者(`members`)には SharePoint 側の仕様で担当者(`owner`)と同じ人も重複して入ってしまうため、アプリ側で「担当者と同名の人物は関係者から除外する」ロジックを入れている（後述 `getMemberNames`）。

### 2.2 複数リスト対応

- ファイル選択は `multiple` 属性で複数ファイル選択可能
- 各タスクに読み込み元ファイル名（拡張子除く）を `_sourceList` として付与し、内部的に統合管理
- 「リスト」フィルタで絞り込み可能（一覧テーブルには列としては表示しない。チャネルで判別できるため）

### 2.3 Setting.json（チーム共有設定）

ファイル名が `Setting.json`（大文字小文字不問）の場合、データではなく設定ファイルとして自動判別・分離読み込みされる。データJSONと同時選択も可。

```json
{
  "statusGroupMap": { "進行中": "稼働系", "未着手": "稼働系", "保留": "保留系" },
  "hiddenPeople": ["退職済みの人の氏名"],
  "groupOrder": ["稼働系", "保留系", "完了・中止"],
  "defaultStatuses": ["未着手", "進行中"]
}
```

保存の二層構成：
1. **Setting.json**（基本・チーム共有、同じ場所に配置してチームで共有）
2. **localStorage**（個人上書き。画面操作は即座に自動保存される。存在する場合はSetting.jsonより優先）

設定タブから「Setting.jsonをダウンロード」でエクスポート、「個人上書きをリセット」でlocalStorageをクリア可能。

## 3. 画面構成（タブ）

上部にタブ切替：**一覧 / チャネル別 / 担当者別 / 設定**

### 3.1 「一覧」タブ

- **サマリーカード**：総件数＋ステータス別件数（クリックでトグル絞り込み、複数選択可）
  - 表示モード切替：「グループ別」（初期値）／「ステータス別」
  - グループ別モード：`statusGroupMap` でグループ化されたステータスは合算1枚のカードに。同グループ内が一部だけ選択中の場合は「一部選択中」の表現（オレンジ破線＋n/m件選択中）
  - 「(未設定)」ステータスは常に先頭（グループ内タイブレークとしても最優先）
- **役割パネル（担当者・関係者・投稿者の集計表）**
  - 表形式：氏名／担当／関係／投稿の列。担当者数の多い順にソート
  - 各数値セルは列内最大値に対する比率でCSSグラデーション背景バー（簡易グラフ表示）
  - 先頭に「(未設定)」行：担当者なし／関係者0人／投稿者なしの件数を集計
  - 行全体をタップ → その人の担当・関係・投稿タグをまとめてON/OFF（3つ全部揃っている場合のみ「有効」表示）
  - 個別の数値バッジをタップ → その役割だけ個別にON/OFF可能（例：担当者と関係者だけ選び、投稿者は除外、という絞り込みができる）
  - この集計は現在の「チャネル」「ステータス」絞り込みを反映する（自分自身の役割タグ選択は除外して計算し、循環参照を防止）
- **フィルタ**：チャネル（プルダウン）／リスト（プルダウン）／条件クリアボタン
- **一覧テーブル**：タイトル（Teamsリンク）／編集リンク（鉛筆アイコン、後述）／ステータス／担当者／関係者／投稿者／チャネル／投稿日／更新日
  - 投稿日・更新日はヘッダークリックでソート切替（▲▼表示）。初期値は投稿日の降順
  - 日付表示は `yyyy/mm/dd`（ゼロ埋め）
  - 担当者・関係者・投稿者は「表示しない人」設定を反映（`getOwnerName`/`getAuthorName`/`getMemberNames` 経由、非表示者は "(未設定)" 扱い）

### 3.2 「チャネル別」タブ

- チャネル × ステータスのマトリクス表（件数）
- 行（チャネル）はチャネル名の五十音順（`localeCompare('ja')`）
- 列（ステータス）は「グループの並び順 → 同グループ内は(未設定)優先 → 件数の多い順」（`statusDisplayComparator` 関数で共通化。他画面のステータス表示順もすべてこれに準拠）
- セルクリック → 一覧タブに遷移し、該当チャネル・ステータスで絞り込み

### 3.3 「担当者別」タブ（タスクボード形式）

- 担当者選択はプルダウン（選択肢に「未完了n／全n」を表示、未完了が多い人が上位）
- 選択するとその人のタスクをステータスごとにカード表示（優先度の高い「未完了」を目立たせる）
  - `RESOLVED_STATUSES`（現在は `['完了']`）に含まれるステータスは自動的に「完了」として折りたたみ表示（`<details>`）
  - 未完了カードは期限（`targetDate`）昇順→期限なしは投稿日降順でソート、期限があれば赤字表示
- ステータス表示のON/OFFチップ（`hiddenStatuses`）で、特定ステータスのセクションを個別に非表示にできる

### 3.4 「設定」タブ

1. **ステータスのグループ化**
   - 各ステータスにプルダウンでグループを割り当て（新規グループ名も作成可、`window.prompt`で入力）
   - グループの並び替え（▲▼ボタン）、名称変更（同グループ内の全ステータスに一括反映）
   - 空になったグループは自動的にリストから消える（`syncGroupOrder`）
2. **表示しない人（退職済みなど）**
   - チェックした人は担当者・関係者・投稿者の選択肢・集計から除外され、"(未設定)" 扱いになる（データ自体は保持）
3. **一覧タブの初期ステータス絞り込み**
   - チェックしたステータスが、データ読み込み時に自動的にサマリーカードでON状態になる

## 4. フィルタ・絞り込みの仕組み（重要）

`getFiltered(options)` が中心のフィルタ関数。`options.exclude` で特定の絞り込み軸だけ除外して再計算できる（例：グラフ自身の選択が自分自身の表示に影響しないようにするため）。

絞り込み軸は以下の3系統：

1. **`activeStatuses`（Set）**：サマリーカードでトグル。複数選択はOR、他の軸とはAND
2. **チャネル／リスト（プルダウン、単一選択）**：`channelFilter` / `listSourceFilter`
3. **`activeRoleTags`（Set）**：役割パネル発。`"owner:氏名"` `"member:氏名"` `"author:氏名"` の形式のタグを持ち、活性化しているタグ群は「いずれか一致すればOK」というOR条件。他の軸とはAND

`activeRoleTags` の `member:(未設定)` は「関係者が0人」、`owner:(未設定)` `author:(未設定)` はそれぞれ getOwnerName/getAuthorName が "(未設定)" を返すケースにマッチ。

過去に存在したが**廃止した仕組み**（Claude Codeで復活させないよう注意）：
- 担当者別の単独棒グラフ（`ownerChart`）→ 役割パネルに統合したため削除
- ステータス別の棒グラフ（`statusChart`）→ サマリーカードのトグルに統合したため削除
- 「自分の役割で絞り込み」の単一選択ドロップダウン（`selfFilter`）→ 役割パネルに置き換え
- 担当者・関係者・投稿者それぞれの単独プルダウン（`ownerFilter`/`memberFilter`/`authorFilter`）→ 役割パネルに統合

## 5. 「表示しない人」ロジックの詳細

- `getOwnerName(item)` / `getAuthorName(item)` / `getMemberNames(item)` の3関数経由でのみ担当者・投稿者・関係者を参照する設計。**`item.owner` 等を直接参照しているコードがあれば、それはバグ（非表示設定が反映されない）**
- `getMemberNames(item)` は以下を満たす名前だけを返す：
  1. `settings.hiddenPeople` に含まれていない
  2. その項目の `item.owner`（担当者）と同名でない（＝担当者と関係者の重複除去）

## 9. 本番移行（SharePoint fetch化）に関する検討結果

現在の「ファイル選択で読み込み」を、本番では `fetch()` に切り替える想定だが、検討の結果、以下の技術的制約が判明している。

1. **SharePointドキュメントライブラリの `.html` は直接開いてもレンダリングされない**
   モダンSharePoint Onlineは `.html` ファイルに強制ダウンロードヘッダーを付与し、ブラウザでの実行を許可しない（セキュリティ上の既定仕様）。
2. **クロスオリジンfetchはCORSでブロックされる**
   ツールを別オリジン（社内HTTPサーバー、GitHub Pages等）に置き、SharePointのデータをfetchしようとするとCORSに阻まれる。回避には基本的にAzure AD (Entra ID) アプリ登録が必要（情報システム部門の確認が必要、未確定）。
3. **OneDriveも別オリジン**（`{テナント}-my.sharepoint.com` は `{テナント}.sharepoint.com` と別ホスト）であり、SharePointへのfetchはCORS対象になる。HTMLの直接レンダリングについても、OneDriveの方がSharePointより開ける場合があるとの非公式情報はあるが、公式に保証された仕様ではなく、本番の前提にはできない。
4. **Power AutomateからオンプレHTTPサーバーへの直接書き込み**にはオンプレミスデータゲートウェイが必要（情シス確認・管理が必要）。

**現時点で最有力の方針**：
SharePointドキュメントライブラリを、社内HTTPサーバー機に「OneDrive同期クライアント」で同期し、同期先ローカルフォルダをそのまま社内HTTPサーバーで配信する。ツール（HTML）とデータ（JSON）が同一オリジンになるため、CORSもAD登録もカスタムスクリプト制限も回避できる。API呼び出し自体が不要になる。

→ この場合、コード上の変更は「ファイル選択(`<input type="file">`)を`fetch(相対パス)`に差し替えるだけ」で済む想定（データ構造・関数群はそのまま流用可能）。

## 11. Thread_Work連携仕様（2026-07-25 要件定義合意・実装は別セッション）

本章は、Task_Dashboardの外部にある「Thread_Tracker」運用（Teams投稿→SharePointリスト→Power Automate→JSON書き出しの一連の仕組み）を、今後「Thread_Work」という新しい仕組みと連携させるための要件定義。**本章の内容はドキュメント化のみで、Task_Dashboard本体（`task-dashboard.html`）への実装はまだ行っていない。**

### 11.1 全体構成

- **①Thread_Tracker**：既存の個別タスク管理の仕組み（変更なし）
- **②Thread_Work（新設・構想段階）**：同一業務に関わる複数タスクを「Work」という単位で束ねる仕組み。専用Workチャネルへの投稿をリスト化し、①のタスクと紐づける
- **③Task_Dashboard**：本ツール。①（＋今後②）のJSONを読み込んで可視化する

### 11.2 Thread_Workの運用設計（有力候補）

1. Workチャネルを新設。チャネルの「モデレーション」機能で新規投稿（＝Work登録）をWork管理者に限定し、返信（進捗共有・タスクリンク蓄積）は誰でも可能にする（Workの細分化・乱立を防止）
2. 稼働中のWorkをWorkチャネルに投稿 → Power AutomateでWork専用SharePointリストへ記録
3. Workリストの列：Workチャネルの`messageId`/`channelId`、**JOBNO**（社内予算単位の業務名）、**ステータス**（稼働中／アーカイブ済 等）
4. Workの目的が終わればアーカイブ（ステータス変更）。アーカイブ済Workは以後①からの新規リンク対象から除外する

### 11.3 ①→②の紐づけ方式（有力候補）

- タスク投稿に専用絵文字（ステータス系絵文字とは別、例：🔗）でリアクションすると、Power Automateがトリガーされる
- トリガー後、Workリストから`ステータス=稼働中`のものだけをOData絞り込みして選択肢を組み立て、Adaptive Cardで提示する
  - SharePoint標準のLookup列にはない「参照先の絞り込み」を、Adaptive Card方式で実現する（Lookup列のピッカー自体には絞り込み機能がないという制約を回避）
- カードは**リアクションした本人への個人チャット（DM）として送信**し、公開スレッドに選択UIを一切表示しない（スレッドが汚れる懸念への対応）
- 選択完了後：
  - ①のタスクリスト該当行に`relWork`／`relChannelId`／`relMessageId`を書き込み
  - ②のWork投稿（Workチャネル）に、そのタスクスレッドへのリンクを**返信**として追加（Work投稿がタスクの索引として機能する）
  - ①のタスクスレッドにも短い確認メッセージ（1行、例：「🔗 Work「○○」に紐づけました」）を返信
- Work進捗・会議の共有はWork投稿への返信で行い、個別タスクの会話は各タスクスレッドに閉じる

### 11.4 ⚠️ 要検証事項（実装着手前に必ず確認）

- **Power AutomateのTeamsリアクショントリガーが「誰が反応したか」のユーザー情報を出力に含むか**、公式ドキュメントで確証が取れなかった（参照時に該当ページが403で閲覧不可）。実機でトリガーを作成し、動的コンテンツにユーザー識別情報（AAD ID等）が出るか検証が必要
- 上記が成立しない場合のフォールバック：Adaptive Cardをスレッドに直接投稿し、応答受信後に「メッセージの更新」アクションで1行の完了表示に圧縮する（カード自体は残るがコンパクト化）
- 真の投稿削除（Graph API）は管理者同意が必要な権限昇格を伴うため不採用（9章のSharePoint fetch化と同種の障壁）

### 11.5 `relUrl`フィールドの提案

既存の`url`はPower Automateが組み立てたTeamsのフルリンクとして書き出されており、`channelId`列は現状常にnullで未使用。Teamsのメッセージdeep linkは`channelId`/`messageId`だけでなく`groupId`/`tenantId`も必要なため、アプリ側でIDから正しいURLを再構成することはできない。よって**新規に`relUrl`（Workアンカー投稿へのフルリンク文字列）をPower Automate側で書き出す**ことを推奨する。`relChannelId`/`relMessageId`は同一Work判定用の内部キーとして扱う。

### 11.6 Task_Dashboard側への影響（実装は別セッション、バックログとして記録）

- **WORK別タブ**：`relWork`ごとのグルーピング表示、ステータス内訳。`relWork`未設定は「(未設定)」のまま一覧に残す
- **WORKフィルタ**：チャネル/リストと同様のプルダウンを追加想定
- **関連スレッドリンク**：`getEditUrl()`と同様のパターンで`getRelatedThreadUrl(item)`を新設想定。`item.relUrl`がある場合のみ表示する
- **Workリスト自体のJSON取り込み**：②のWorkリスト（JOBNO・ステータス含む）もJSON書き出しし、「WORK別」タブでJOBNO表示・アーカイブ済のグレーアウトに利用する想定
- **日次スナップショット/トレンド**：ステータス別件数推移・担当者別残タスク数推移をPower Automate側の日次サマリー書き出しに依存。完了リードタイム分布（`date`→`completedDate`）は既存データのみで実装可能（外部依存なし）
